# DAY 6 · Яндекс Метрика и допуск к запуску

## Настройки и события

Аналитика выключена по умолчанию. В браузере действует только на HTTPS-адресе
`mprof-seller.ru` при `NEXT_PUBLIC_MPROF_METRIKA_ENABLED=true` и после
отдельного разрешения. Сервер дополнительно требует `MPROF_METRIKA_ENABLED=true`
и канонический `NEXT_PUBLIC_SITE_URL`. Никакого скрипта Яндекса, Вебвизора,
записи форм, `noscript`-пикселя или автосбора данных в кабинете.

Яндекс получает от сервера только выбранный путь, случайный числовой ClientID,
разрешённые метки и фиксированные значения событий. Путь не содержит query
авторизации и оплаты. Утверждённые рекламные значения перечисляются через запятую
в `NEXT_PUBLIC_MPROF_METRIKA_CAMPAIGN_VALUES`. Не включать в список ФИО, контакты,
идентификаторы клиентов и произвольный пользовательский ввод. `yclid` принимается
только как числовая рекламная метка. Источник первого посещения связывается
с браузером после разрешения и сохраняется при переходе в кабинет.

| Действие | Учёт |
|---|---|
| Просмотр | `pageview` на разрешённый маршрут, один вызов на переход |
| Подтверждённая регистрация | `registration_confirmed`, подлинный пользователь Auth и подтверждённый email |
| Первый бесплатный расчёт | `first_free_calculation`, зафиксированная операция с первым расходом |
| Начало checkout | `checkout_started`, новое серверное намерение |
| Успешная оплата | `payment_confirmed`, запись подтверждённой выдачи, без дохода |
| Разовая покупка | `purchase_149`, ценность цели 149 RUB |
| Первая активация | `subscription_449`, ценность цели 449 RUB |
| Продление | `subscription_renewed`, ценность цели 449 RUB |
| Терминальный отказ | `payment_failed`, отменённое намерение с проверенной привязкой |

В счётчике нужны цели «JavaScript-событие» с этими идентификаторами. Просмотры
доступны в стандартных отчётах и отдельной цели не требуют. Для дохода по каналам
суммировать только три денежные цели. Для CAC нужны фактические расходы из
Директа или импорта и число новых платящих клиентов, а не число повторных оплат.
До сверки с реальным счётчиком финансовым источником остаются записи выдачи.

## Серверная очередь и эксплуатация

При согласии запись создаётся в одной транзакции с квитанцией, намерением
или расчётом. Составной уникальный ключ удерживает один экземпляр каждого
события. Внешний идентификатор — HMAC от случайного идентификатора записи и типа
события. Реальные номера платежей и идентификаторы аккаунтов остаются в M-PROF.

Перед включением выполнить отдельный релиз миграции. Настроить
`MPROF_METRIKA_COUNTER_ID`, серверные `MPROF_METRIKA_MEASUREMENT_TOKEN`,
`MPROF_METRIKA_EVENT_KEY` и `MPROF_METRIKA_DRAIN_TOKEN`. Для трёх секретов
использовать закрытую конфигурацию. Регулярный HTTPS POST на `/api/metrika/drain`
с отдельным bearer вызывает обработку небольшими порциями. Настроить
интервал короче 12 часов и контроль состояний `sending`, `uncertain`, `expired`,
`rejected`. По подтверждённому ответу поставщика отмечается `sent`.
Запрос с неопределённым результатом и запись после аварии в `sending`
сверяются перед любым повтором. У API не подтверждена идемпотентность
JavaScript-целей. Просроченные события требуют ручного решения и проверки
официального импорта офлайн-конверсий.

Проверить реальным счётчиком разрешение и отказ, два SPA-перехода, обновление,
регистрацию после подтверждения, три сценария платы, повтор уведомления и
разрыв ответа. Использовать синтетические данные и тестовую ЮKassa.
Проверить в Метрике привязку рекламного источника и суммы. Вебвизор,
автоматические контактные цели и запись форм оставить выключенными.

Источники: [Measurement Protocol](https://yandex.ru/dev/metrika/ru/data-import/measurement-about),
[параметры передачи](https://yandex.ru/dev/metrika/ru/data-import/measurement-upload),
[офлайн-конверсии](https://yandex.ru/dev/metrika/ru/management/offline-conv).

## Юридический допуск

- `/privacy`, `/offer` и `/contacts` существуют. Оферта указывает статус
  исполнителя, ИНН и контакт, описывает оплату, сроки и способ связи по возврату.
  Отдельной страницы пользовательского соглашения и отдельного согласия на
  регистрацию в проверенной версии нет. Владелец должен подтвердить, какие
  условия регулируют бесплатный доступ и на каком основании обрабатываются
  данные регистрации. Реквизиты сверить с актуальными данными владельца.
- Часть 1 статьи 9 152-ФЗ требует отдельного оформления согласия, когда
  используется это основание. Технический выбор аналитики реализован отдельно.
  До включения необходимо согласовать текст согласия, данные получателя, объём
  идентификаторов, длительность хранения и механизм отзыва для серверной очереди.
  Случайный ClientID и рекламная метка могут оставаться персональными данными
  в контексте связывания, даже при отсутствии контактов.
  [156-ФЗ, ст. 5](https://publication.pravo.gov.ru/document/0001202506240021)
- Регион проекта Supabase подтверждён через Supabase Management API, `eu-central-1`.
  Регистрация вызывает Supabase Auth напрямую. Пока не подтверждено размещение
  первичного сбора данных граждан РФ в России и применимое исключение,
  локализация является блокером коммерческого запуска. Отдельно проверить
  трансграничную передачу и необходимость уведомлений по статьям 12 и 22.
  [23-ФЗ](https://publication.pravo.gov.ru/document/0001202502280034) ·
  [152-ФЗ](https://mintrud.gov.ru/docs/laws/130) ·
  [Форма Роскомнадзора](https://pd.rkn.gov.ru/cross-border-transmission/form2/)
- Оферта предлагает индивидуальное рассмотрение возврата. Для покупателей,
  подпадающих под защиту потребителей, проверить применимость статьи 32 и
  формулировки о праве на отказ, фактических расходах и порядке возврата.
  Маршрут возврата ЮKassa и техническое снятие права не определяют наличие
  права потребителя на денежный возврат.
  [Роспотребнадзор о подписках](https://www.04.rospotrebnadzor.ru/index.php/consumer-information/faq/17576-09112022.pdf)
