# Тестовый магазин и приёмка платежей DAY 5

В доступном кабинете ЮKassa 25 ноября 2026 года не найден тестовый магазин:
доступны основной магазин M-PROF и прежний временно неработающий магазин.
Локальная конфигурация тестовых credentials не обнаружена. Реальные платежи,
карты и production-заказы для проверки не использовались.

Проверки с заглушкой API и настоящим изолированным PostgreSQL доказывают
идемпотентность M-PROF, но не заменяют checkout и webhook тестового магазина.

Для внешней приёмки владелец должен:

1. Выбрать или создать тестовый магазин ЮKassa и подтвердить его тестовый режим.
2. Сохранить ShopID и тестовый секретный ключ в защищённой конфигурации отдельного
   стенда. Не отправлять ключ в чат, Git или браузерный bundle; production-ключи
   не копировать. Стенд должен использовать отдельную БД и синтетические аккаунты.
3. Указать HTTPS webhook URL именно этого стенда и return URL этого же стенда.
   Не перенастраивать production-магазин или production webhook.
4. Перед оплатой проверить тестовый режим магазина и `test: true` в объекте
   платежа. Использовать только опубликованные ЮKassa тестовые реквизиты.
   Для каждого тарифа отдельно пройти checkout → тестовая оплата → webhook →
   серверная перепроверка → одно право → использование оплаченной функции.

Обязательны повтор запроса после потери ответа, параллельный webhook, проверка
отмены и повторной осознанной покупки. Для 149 ₽ — ровно один дополнительный
manual/XLSX-расчёт, без Ozon API и AI. Для 449 ₽ — 30 дней безлимита, Ozon API
и AI, продление от максимума текущего оплаченного срока и времени БД.

Статус возврата отделён от начисления прав. До согласования бизнес-правила
отзыва уже израсходованного кредита/продлённой подписки `refund.succeeded`
возвращает `503 refund_review_required`, не удаляя оплаченные права. Это
ограничение приёмки, а не завершённая автоматическая обработка возврата.

## Порядок выпуска после отдельного разрешения

1. Завершить приёмку в тестовом магазине и получить успешную Linux CI для
   точного SHA релиза. Зафиксировать предыдущий активный SHA приложения.
2. Перед переключением проверить существующие незавершённые заказы без
   привязки к `payment_intents`. Сверить их статусы с ЮKassa. Старые заказы
   обрабатываются по сохранённым идентификаторам. Первый checkout после
   переключения может создать новое намерение для пользователя со старым
   незавершённым заказом. Закрыть такие случаи до открытия checkout на новой
   версии, особенно если результат старого платежа неизвестен.
3. По отдельному разрешению применить аддитивную миграцию
   `20261125155702_payment_intents.sql` до выпуска приложения. Сверить SHA-256,
   точку восстановления и блокировки. После COMMIT проверить RLS и `EXECUTE`
   для пяти новых RPC, обновить кэш схемы PostgREST и проверить видимость
   сигнатур. Объекты PR #120 и его миграцию этот выпуск не затрагивает.
4. После отдельного разрешения на deploy сверить активный SHA и healthcheck.
   Проверить получение статусов существующих заказов. Проверку с оплатой
   выполнять только на изолированном стенде ЮKassa.
5. При ошибке выпуска вернуть предыдущий SHA по согласованной процедуре и
   сохранить новые таблицы и журнал попыток для сверки. Повторный checkout
   для попыток с неизвестным статусом открывать лишь после сверки с ЮKassa.
   Откат на старый обработчик не переносит в него новую защиту от дублей.
