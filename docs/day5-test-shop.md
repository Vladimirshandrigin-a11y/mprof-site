# Тестовый магазин и приёмка платежей DAY 5

В разделе «Тестовые» кабинета ЮKassa есть магазин `1544975` для M-PROF.
Локальный стенд использует его отдельно от действующего магазина `1432087`.
Настройки подключения хранит только локальная конфигурация стенда.

Проверки с заглушкой API и настоящим изолированным PostgreSQL доказывают
идемпотентность M-PROF, но не заменяют checkout и webhook тестового магазина.

Для повторной сквозной приёмки:

1. Подтвердить тестовый режим нового магазина в списке сервисов ЮKassa.
2. Запустить checkout из SHA PR #129 с отдельным Supabase Auth и PostgreSQL.
   Для пустой локальной Supabase-базы использовать итоговый `supabase/schema.sql`.
   Для уже существующей изолированной базы с базовой схемой использовать
   миграцию `20261125155702_payment_intents.sql`. Создать синтетические аккаунты.
3. Указать собственные URL приложения и API Supabase в `NEXT_PUBLIC_SITE_URL`
   и `NEXT_PUBLIC_SUPABASE_URL`. Настроить локальные ключи Supabase и серверные
   `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` только из тестового магазина. Хранить
   ключ вне checkout Git, в файле `0600` под каталогом `0700`. Перед запуском
   сверить ShopID и тестовый формат ключа. Для доставки запустить отдельный
   loopback-прокси: он принимает только `POST /api/payment/webhook` с JSON,
   пропускает только разрешённые события и отправляет в приложение только
   тип, событие и ID объекта. Туннель направлять на прокси. Перед сохранением
   URL проверить TLS, `404` на `/`, `/app`, `/auth/v1/health` и `/api/payment/create`,
   `400` на пустой JSON webhook. Подписать тестовый магазин на
   `payment.succeeded`, `payment.canceled` и `refund.succeeded`.
4. Перед оплатой проверить тестовый режим магазина и `test: true` в объекте
   платежа. Использовать опубликованные ЮKassa тестовые реквизиты.
   Для каждого тарифа отдельно пройти checkout → тестовая оплата → webhook →
   серверная перепроверка → одно право → использование оплаченной функции.
5. Сопоставить полученное по HTTPS событие, статус из API ЮKassa и одиночную
   запись выдачи в локальной БД. Для проверки повтора доставить тот же ID
   параллельно в локальный обработчик. Использовать один UUID намерения для
   всех повторов. Для продления явно создать новое намерение того же аккаунта.
6. После приёмки отключить подписки и временный туннель. Проверить, что
   HTTPS больше не отвечает через стенд, а локальные данные и закрытая
   конфигурация сохранились. В журнале достаточно событий и итогов HTTP,
   без шаблонов запросов с ключами, банковских реквизитов и токенов.

Обязательны повтор запроса после потери ответа, параллельный webhook, проверка
отмены и повторной осознанной покупки. Для 149 ₽ — ровно один дополнительный
manual/XLSX-расчёт, без Ozon API и AI. Для 449 ₽ — 30 дней безлимита, Ozon API
и AI, продление от максимума текущего оплаченного срока и времени БД.

## Подтверждённые возвраты

Раздел 6 [публичной оферты M-PROF](https://mprof-seller.ru/offer) предусматривает
индивидуальное рассмотрение обращения. Решение о возврате и инициирование
денежной операции остаются у владельца. Обработчик `refund.succeeded` получает
возврат и исходный платёж через GET ЮKassa, сверяет привязку, статус, валюту и
сумму, затем фиксирует результат в `payment_refunds`. Ключ журнала — `refund_id`.

- Полный возврат 149 ₽ отзывает активный кредит, когда профиль показывает ноль
  или один расход расчётов. Первая попытка бесплатная. При большем расходе счётчик
  не указывает, какой платёж потрачен. Такие случаи остаются на ручной обработке.
- Полный возврат 449 ₽ отзывает подтверждённые 30 дней на конце срока. Должны
  совпасть профиль, подписка и запись о выдаче. Возврат более раннего платежа под
  последующими продлениями и неподтверждённое происхождение срока требуют ручной
  обработки. Сроки других платежей сохраняются.
- Частичные возвраты требуют ручной обработки. Успешный полный возврат до
  начисления блокирует поздний webhook оплаты и повторную выдачу старым кодом.

Очередь для владельца хранится в строках `public.payment_refunds` с `outcome`
`review_partial`, `review_single_usage` и `review_unlimited_attribution`.
Повтор webhook возвращает сохранённое решение. Регрессии проверяют гонки и
отсутствие изменения уже сделанных расчётов. Сквозной сценарий возврата выполняется
в будущем только в тестовом магазине.

## Старые заказы перед выпуском

Read-only срез production на 26 ноября 2026 года: 25 заказов ЮKassa, из них
14 `active`, 4 `cancelled`, 7 `failed` и 0 `pending`. Повторяющихся сохранённых
`provider_payment_id` нет. У всех 7 `failed` ID провайдера отсутствует. Из них
6 относятся к одной паре аккаунт/тариф, а 5 из 7 имеют активный заказ того же
аккаунта и тарифа в пределах суток. Эти признаки дают кандидатов для сверки,
статус платежа по ним из базы установить нельзя.

Сверить 7 `failed` в кабинете по времени, сумме и метаданным до открытия checkout
новой версии. Проверенная миграция аддитивна и сохраняет текущие строки и доступ.

## Порядок выпуска после отдельного разрешения

1. Зафиксировать проверенный SHA PR и SHA активного приложения для отката.
   Получить успешную Linux CI, приёмку магазина, webhook и возвратов для
   проверенного дерева. Гейт выпуска — согласованная сверка старых заказов,
   готовая точка восстановления и проверенный способ временно закрыть создание
   заказа отдельно от webhook. Если инфраструктура пока не умеет блокировать
   этот маршрут, заранее согласовать и отрепетировать отдельный временный гейт.
2. Зафиксировать проверенную резервную копию или точку PITR непосредственно
   перед окном, проверить доступность восстановления на отдельной базе.
   Зафиксировать срез `pending` и `failed` и последние активации. Сопоставлять
   заказы по `metadata.subscription_id` с проверкой магазина, валюты, суммы и
   статуса провайдера. Совпадения времени и суммы использовать для поиска
   кандидатов. По подтверждённой оплате без права остановить выпуск и вынести
   корректировку на отдельное согласование.
3. Временно закрыть только `POST /api/payment/create` с ответом `503`, оставить
   `/api/payment/webhook` и чтение заказов доступными. Дождаться окончания
   уже начатых запросов во всех инстансах. Окончание окна ожидания подтвердить
   логами и свежим read-only срезом. Отдельно сверить ссылки и заказы с
   неизвестным результатом, поскольку они могли стать оплаченными позднее.
4. Применить `20261125155702_payment_intents.sql` по отдельному разрешению.
   Сверить хэш с проверенным деревом и открыть отдельный сеанс `verify-full`.
   Проверить неожиданные транзакции и блокировки, выставить и подтвердить
   `lock_timeout=5s`, `statement_timeout=60s`, `transaction_timeout=120s`.
   Выполнить файл с остановкой при первой ошибке. В файле свои `BEGIN/COMMIT`.
   При неизвестном COMMIT сначала проверить каталоги read-only. После COMMIT
   подтвердить сохранность старых прав, RLS, сервисные grants и сигнатуры
   шести новых RPC после перезагрузки кэша PostgREST.
5. Выполнить merge по отдельному разрешению. Сверить дерево merge-коммита с
   протестированным деревом. При расхождении повторить CI до выпуска. Выполнить
   ручной production-деплой этого SHA и подтвердить build, healthcheck и
   запущенный SHA. Автодеплой оставить выключенным.
6. При закрытом создании заказов проверить публичную доступность, вход, права
   и чтение существующих заказов, отказ без сессии, доступ к RPC только у
   сервисной роли, отсутствие ошибок webhook. После сверки целей открыть
   создание заказов. Контролировать реальные поступающие оплаты пассивно без
   тестовых платежей в production. Остановить открытие при расхождении прав,
   ошибках schema cache или неопределённом статусе миграции.
7. При откате снова закрыть создание заказов и вернуть зафиксированный SHA.
   Сохранить SQL, `payment_intents`, журналы и маршрутизацию безопасной
   обработки webhook. Старый checkout снова создаёт новый заказ на каждый
   запрос. Старый обработчик также не применяет возвраты нового формата.
   Если активен только старый обработчик, зафиксировать входящие события
   возврата для последующей сверки и повторной обработки новым кодом.
   Открыть старый checkout только по отдельному решению после сверки попыток.

Между миграцией и деплоем старый webhook оплаты сохраняет возможность выдачи
для старых заказов. Запись подтверждённого полного возврата ограждает повторную
выдачу. Главный риск этого промежутка — старый checkout всё ещё способен
создавать новые заказы с новым ключом на каждый повтор. Поэтому приостановка
касается создания заказов и действует до подтверждения нового runtime.
